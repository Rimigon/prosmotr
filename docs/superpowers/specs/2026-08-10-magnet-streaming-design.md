# Магнет-стриминг в «Просмотре» — дизайн

Дата: 2026-08-10
Статус: утверждён пользователем, спека к ревью
Скоуп: первая версия (v1)

---

## 1. Проблема и цель

Пользователь хочет: открыть «Просмотр», вставить магнет-ссылку, и через короткое время
смотреть фильм — без установки отдельного торрент-клиента и без ожидания полной загрузки.

Цель v1: встроенный торрент-движок (**MonoTorrent 3.0.x**, чистый .NET, NuGet), который
качает выбранный видеофайл **последовательно** во временный файл, а **LibVLC** (уже есть
в проекте) играет растущий файл. Никаких внешних зависимостей — приложение остаётся
самодостаточным, как сейчас с LibVLC/Magick.

Решение пользователя, зафиксированное на этапе брейншторма:

- Встроенный движок (не внешний qBittorrent, не Node-хелпер).
- Контент: в основном одиночные фильмы; папки-сезоны вне скоупа v1 (берём самое большое
  видео в торренте, UI-выбор — потом).
- Судьба файла: **кэш + раздача** — файл живёт в кэш-папке, приложение раздаёт, пока открыто;
  настройка «удалять при выходе» (по умолчанию выкл).
- Точка входа: кнопка на стартовом экране + подхват магнета из буфера обмена при запуске +
  тумблер регистрации `magnet:` протокола (по умолчанию выкл).

## 2. Пользовательские сценарии

1. **Основной:** пользователь открывает приложение (пустой экран) → «Смотреть по магнет-ссылке»
   → вставляет `magnet:?xt=urn:btih:...` → видит экран загрузки (название, %, скорость, пиры) →
   через ~10–30 с (при хорошей раздаче) начинается воспроизведение; перемотка назад мгновенная,
   вперёд — «докачивается…».
2. **Из буфера:** приложение запущено, буфер обмена содержит валидную магнет-ссылку →
   предложение «Вставить ссылку из буфера?».
3. **Повторный заход:** тот же магнет вставляется снова → загрузка продолжается с места
   (fast-resume), а не с нуля.
4. **Ошибка:** нет пиров/метаданных за таймаут → понятное сообщение → возврат на стартовый экран.

## 3. Архитектура

Новый «режим» приложения, изолированный от галереи. `MainViewModel.CurrentContent` получает
ещё один тип VM — `TorrentStreamViewModel`, для которого в `MainWindow.xaml` регистрируется
неявный `DataTemplate` → `TorrentStreamView` (по существующему паттерну VM→View).

```
┌─ Пользователь ─────────────────────────────────────────────┐
│  EmptyStateView (кнопка) / буфер обмена / magnet: протокол │
└──────────────┬─────────────────────────────────────────────┘
               ▼
        MainViewModel.OpenMagnetAsync(magnet)      [partial: Gallery или новый файл]
               ▼
        ITorrentEngineService.AddMagnetAsync(magnet)
        └── TorrentSession (ObservableObject):
              Статус: ResolvingMetadata → Downloading → Ready → Playing → Error/Stopped
              Прогресс %, скорость, пиры, ETA, выбранный файл, путь к temp-файлу
               ▼ (по событию Ready)
        MainViewModel: CurrentContent = TorrentStreamViewModel(session, vlc)
               ▼
        TorrentStreamView: LibVLCSharp.WPF VideoView играет поток StreamProvider
               (MediaPlayer + StreamMediaInput), данные параллельно пишутся в кэш на диск
```

### Ключевое решение: streaming-режим MonoTorrent (проверено по исходникам 3.0.2)

Проверка исходников MonoTorrent показала: **«последовательной загрузки» в обычном режиме нет**
(в `TorrentSettings` нет sequential-флага; раrest-first для файла с дырами VLC играть не может).
Единственный штатный механизм «скачивать по мере чтения» — **streaming-режим**:

- `engine.AddStreamingAsync(MagnetLink, saveDir)` → `TorrentManager` (стриминговый piece-requester:
  запрашивает куски, начиная с текущей позиции потока).
- `StreamProvider.CreateStreamAsync(file, prebuffer: true)` возвращает **seekable-поток**;
  `prebuffer: true` скачивает **первый и последний куски** до готовности потока — это штатно
  решает проблему MP4 с moov в конце (VLC получает метаданные сразу).
- VLC играет поток через кастомный IO LibVLCSharp: `new Media(libVlc, new StreamMediaInput(stream))`
  (`StreamMediaInput` есть в LibVLCSharp 3.9.7.1 — проверено по тегу). Связка доказана рабочим
  примером автора LibVLCSharp (LVST: MonoTorrent.Streaming + LibVLCSharp).
- Данные всё равно **пишутся на диск** (DiskManager, `LocalStream.ReadAsync` читает из
  `DiskManager`), поэтому «кэш + раздача» сохраняется: файл материализуется в saveDir.
- Перемотка вперёд за пределы скачанного: поток блокирует чтение, движок качает с этой позиции —
  оверлей «докачивается…» поверх плеера (по позиции VLC vs прогресс Bitfield).
- Риск, оставшийся у кастомного IO: поведение VLC при медленном/блокирующем чтении (проба,
  seek к moov). Митигация: prebuffer + тесты вручную; запасной вариант — файл на диске после
  докачки первого фрагмента (см. раздел 8).

## 4. Компоненты

### 4.1. `ITorrentEngineService` / `TorrentEngineService` (новый, `Services/Torrent/`)

Singleton в DI (паттерн `LibVlcProvider`/`MediaLibraryService`).

- `Task<TorrentSession> AddMagnetAsync(string magnet, CancellationToken ct)`
  — парсит через `MagnetLink.TryParse`, создаёт `ClientEngine` (если ещё нет), вызывает
  `AddStreamingAsync`, ждёт метаданные (`WaitForMetadataAsync` + таймаут 60 с), выбирает файл,
  создаёт поток (`StreamProvider.CreateStreamAsync(file, prebuffer: true)`) и ставит сессию
  в статус `ReadyToPlay`.
- `TorrentSession? GetActiveSession()` — текущая сессия.
- `Task StopAsync(session)` — остановка: `engine.RemoveAsync(manager, …)`, fast-resume
  (автосохранение через `EngineSettings.AutoSaveLoadFastResume = true`).
- `Task ShutdownAsync()` — остановка всех сессий; при `DeleteTorrentCacheOnExit` — удаление данных.
- Владеет одним `ClientEngine` (движок на всё приложение; сессия — одна, v1).

Выбор файла: из `manager.Files` берём самый большой файл с видео-расширением
(список из `SupportedFormats` + `.mkv/.avi/.webm/.mp4/.mov/.ts/...`) — чистая функция
`TorrentFileSelector` (тестируется без сети). Если видео нет — ошибка.

### 4.2. `TorrentSession` (новый, `Models/` или `Services/Torrent/`)

Observable-модель одной загрузки. Поля: `InfoHash`, `Name`, `SelectedFile` (путь, размер),
`Status` (enum), `ProgressPercent`, `DownloadSpeed`, `UploadSpeed`, `PeersCount`, `EtaSeconds`,
`IsReadyToPlay` (флаг «можно запускать плеер»), `Stream` (seekable-поток из `StreamProvider`,
создаётся на этапе ReadyToPlay), `TempFilePath` (путь на диске, куда пишется файл),
`ErrorMessage`.

### 4.3. `TorrentStreamViewModel` (новый, `ViewModels/`) + `TorrentStreamView` (новый, `Views/`)

- Подписан на `TorrentSession.PropertyChanged`; умеет:
  - `Play()` — создать `MediaPlayer` на общем `LibVlcProvider`, открыть поток из сессии
    (`new Media(libVlc, new StreamMediaInput(session.Stream))`), play.
  - `Stop()` — остановить плеер, освободить (паттерн `VideoViewerViewModel.StopAndRelease`).
  - `ToggleFullScreen()` — через существующий `FullScreenHelper` (тот же путь, что у фото/видео).
  - `CloseSession()` — стоп сессии, возврат к `EmptyState` (`MainViewModel`).
- View: две фазы (DataTrigger/видимость):
  - **Загрузка:** название, крупный прогресс, скорость ↓/↑, пиры, ETA, кнопка «Отмена».
  - **Воспроизведение:** `LibVLCSharp.WPF VideoView`, минимальная панель: play/pause, seek
    (в пределах скачанного; ползунок знает `DownloadedBytes`), громкость, mute, полный экран,
    кнопка «Закрыть сессию».
  - Оверлей «докачивается…» при seek вперёд за границу скачанного (позиция VLC vs
    прогресс `Bitfield`).
- Панель/хоткеи: v1 — минимально (пробел play/pause, Esc — выход из полноэкранного, Esc дважды —
  закрыть сессию; без сложного автоскрытия). Airspace-нюансы LibVLC применяются как в
  `VideoViewerView` (чёрный cover, фокус окну).

### 4.4. Входы

- `EmptyStateView`: кнопка «Смотреть по магнет-ссылке…» + вызов `MainViewModel.OpenMagnetCommand`.
- Диалог вставки: простое окно (паттерн `SettingsWindow`/диалог) с `TextBox`, валидация
  `magnet:?xt=urn:btih:` (case-insensitive), кнопки ОК/Отмена.
- Буфер обмена: при `InitializeAsync` (пустой старт, без аргументов) проверить
  `Clipboard.ContainsText()` на валидную магнет-ссылку → предложить (диалог Да/Нет).
- `magnet:` протокол: тумблер в настройках (выкл по умолчанию) → регистрация в HKCU
  (паттерн `FileAssociationService`); при запуске с `magnet:` аргументом → сразу открыть сессию.

### 4.5. Настройки (`AppSettings`, новая секция «Магнет-стриминг»)

- `TorrentCacheDirectory` (string, по умолчанию `%LOCALAPPDATA%\Prosmotr\torrents`) — v1: поле
  в модели, в окне настроек можно показать путь (редактирование — потом).
- `DeleteTorrentCacheOnExit` (bool, default `false`) — удалять скачанное при выходе.
- `RegisterMagnetProtocol` (bool, default `false`).
- `TorrentReadinessBytes` — **не нужен**: «готово к воспроизведению» определяется самим
  `StreamProvider.CreateStreamAsync(file, prebuffer: true)` (он завершается, когда скачаны
  первый и последний куски). В настройки не выносим.

### 4.6. Кэш и fast-resume

- Структура: `<cache>\<infoHash>\` — данные торрента пишутся туда (saveDirectory).
  Fast-resume: `EngineSettings.AutoSaveLoadFastResume = true` (по умолчанию) — MonoTorrent сам
  сохраняет/загружает fast-resume по `GetFastResumePath(InfoHashes)` при остановке/старте.
- Cleanup при выходе: `App.OnExit`/`MainViewModel.Dispose` → `TorrentEngineService.ShutdownAsync()`
  (стоп сессии, fast-resume; при `DeleteTorrentCacheOnExit` — удаление данных сессии
  через `RemoveAsync(manager, RemoveMode.Data…)`).
- Раздача продолжается, пока приложение открыто и сессия активна.

## 5. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Невалидная ссылка | Ошибка в диалоге, ничего не создаём |
| Нет метаданных за 60 с | Сообщение «Не удалось получить метаданные (нет пиров)», возврат |
| Нет видеофайла в торренте | Сообщение «В торренте нет видеофайла», возврат |
| Нет места на диске | Перехват `IOException` → сообщение, очистка сессии |
| Нет пиров после старта | Экран загрузки висит на 0% с понятным текстом; пользователь может отменить |
| Ошибка плеера | Оверлей ошибки + возможность закрыть сессию |
| Закрытие окна во время загрузки/воспроизведения | Стоп сессии + fast-resume (файл не удаляем, если не включена очистка) |

## 6. Тесты

Юнит (без сети, паттерн `tests/Prosmotr.Tests`):

- Парсинг/валидация магнет-ссылок (`MagnetLinkParser`: валидные/невалидные, регистр, лишние
  параметры `&dn=`, `&tr=`).
- Выбор видеофайла в торренте (`TorrentFileSelector`: самый большой видеофайл; торрент без
  видео → ошибка).
- (Опционально) вычисление пути кэша.

Интеграция вручную (не в CI, нужна сеть): реальный легальный магнет, проверка
«вставил → загрузилось → играет → перемотка», повторный заход (fast-resume), MP4 с moov в конце
(проверка prebuffer).

## 7. Вне скоупа v1

- Выбор файла в сезонных папках (берём самое большое видео).
- Стриминг без записи на диск (всё в памяти): данные пишутся на диск — это требование
  «кэша + раздачи».
- Внешние субтитры из торрента (встроенные в контейнер работают через VLC сами).
- Лимиты скорости, выбор порта, UPnP.
- Прокси/интеграция с VPN.
- Раздача «навсегда» (после закрытия сессии).

## 8. Риски

1. **Кастомный IO VLC (StreamMediaInput)**: проба/seek VLC по блокирующему потоку может
   вести себя иначе, чем локальный файл (медленное чтение при недоскачанных кусках).
   Митигация: `prebuffer: true` (первые+последние куски до старта), ручное тестирование
   на реальных магнетах. Запасной вариант: после докачки первых фрагментов играть
   **файл с диска** (он растёт) — но в обычном (не streaming) режиме MonoTorrent качает
   rarest-first, поэтому fallback требует своего piece-requester'а; держим в уме, не планируем.
2. **VLC «зависает» на блокирующем чтении** при seek вперёд за скачанный диапазон:
   ползунок ограничиваем скачанным диапазоном + оверлей «докачивается…»; поток сам качает
   с позиции seek (свойство `LocalStream`).
3. **Один поток на менеджер**: `StreamProvider` разрешает один активный поток; в v1 сессия одна.
4. **DHT/трекеры за NAT** — для старта нужны исходящие + DHT bootstrap; встроенный bootstrap
   MonoTorrent достаточен для популярных раздач (проверяется в интеграции).

## 9. Что не трогаем

Галерея, навигация, удаление, PiP, превью таймлайна, clone-режим — не изменяются.
`VideoViewerViewModel` не трогаем: торрент-плеер — отдельный VM с минимальной панелью
(переиспользуем только `LibVlcProvider`, `FullScreenHelper`, `ToastView`/`INotificationService`).
